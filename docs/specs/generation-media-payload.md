# Spec: 生成请求内联素材（问题）

状态：问题已确认，尚未开始实现。属于 [capability-map.md](./capability-map.md) 的媒体与生成边界。代码考古、方案对比和待确认项见 [generation-media-payload-investigation.md](./generation-media-payload-investigation.md)。

## 问题

账号模式下，画布生成把参考图、参考视频、参考音频以 base64 data URL **内联进 `POST /api/generations` 的 JSON 请求体**。但这些素材本来就已经是服务器上的资产：它们有 `user_media` 记录、有 `remote:<id>` 编号、字节存在服务端磁盘或 MinIO。

浏览器因此做了一件多余的事：把服务器已经存着的字节重新读出来、base64 编码一遍、再传回同一台服务器。

## 实测数据

一次三参考素材的视频建任务（模型 `seedance-2.0-mini-offical`，15 秒，720x1280，参考模式），请求体 **29,552,678 字节（约 29.5MB）**。

计算依据是审计日志的截断标记：`truncateJson`（`server/src/log.ts`）输出 `…[truncated N chars]`，其中 N = 原始 JSON 长度 − 16384，该条日志 N = 29,536,294。

组成能对上账：

| 参考素材 | 字节数 | base64 后（×4/3） |
| --- | --- | --- |
| 参考视频 `8f326f68` | 19,878,018 | 26,504,024 |
| 参考图 `2a5890b1` | 1,292,809 | 1,723,745 |
| 参考图 `f169e83b` | 989,256 | 1,319,008 |
| 合计 | 22,160,083 | 29,546,777 |

与实测 29,552,678 只差 5,901 字符（提示词和 JSON 结构），可以认定请求体基本全部由内联素材构成。

## 影响

1. **参数错误反馈慢。** 素材先传完、上游收完才做参数校验，所以一个时长越界要等 21.2 秒和 27.5 秒才返回；上游网关不可用时等过 125.7 秒和 125.8 秒。
2. **失败要重传。** 每次重试都重新读盘、重新 base64、重新传几十兆；用户中途关页面就白传（线上有连续三条 `request aborted`）。
3. **建任务慢。** 同一条成功建任务实测 17 秒，其中大部分是传素材。
4. **日志被迫打补丁。** 素材字节会灌进审计日志，因此需要专门做素材摘要（见 CHANGELOG 的审计日志素材脱敏）；而截断从字符串头部开始时，又会把后面的参数和素材清单挤掉。
5. **请求体不设防。** `express.json({ limit: Infinity })`（`server/src/app.ts`），没有任何上限。
6. **生成记录没有素材溯源。** 任务行只保存 `operation`（上游任务号、adapter、模型），不保存用过哪些素材，所以事后无法回答「这条片子用了哪几张参考图」。
7. **客户端与上游方言耦合。** 浏览器在拼 `resolution_name`、`generate_audio`、`watermark`、`videoMode` 这些上游字段，服务端还按这套方言校验，上游改参数名就要前后端一起改。

## 根因

这不是「忘了优化」，是双模式架构的遗留：

- 本地模式（`VITE_AUTH_BYPASS=true`）下浏览器直连上游，**必须**自己拼 base64，因为浏览器就是上游的客户端。
- 账号模式引入服务端代发时，**服务端入参契约照抄了上面那套报文**，而不是围绕「素材已经在服务端」重新设计。证据见调研文档的代码考古一节。
- 结果：账号模式已经由服务端承担上游客户端角色，浏览器却还在按上游客户端的方式组装载荷。

## 边界（本轮不做什么）

- 不改本地模式的直连实现。
- 上游那一跳仍然是 base64：上游协议只接受 data URL 形式的参考素材，省掉的是浏览器那一跳。
- 不为此新增「模型能力表」；参数校验以上游为准，本问题只负责让上游能尽快收到请求并尽快返回结论。
