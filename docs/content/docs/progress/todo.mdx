## 生成链路

- **参考素材内联 base64，请求体可达数十 MB（已确认，待处理）**：画布视频生成把参考图、参考视频、参考音频一律以 data URL 内联进 `POST /api/generations` 的 JSON，每次生成都重传全部素材。
  - 实测（线上 10:59 一次成功的三参考素材视频建任务）：请求体 **29,552,678 字节 ≈ 29.5MB**。依据是审计日志的截断标记：`truncateJson`（`server/src/log.ts`）输出 `…[truncated N chars]`，其中 N 为「原始 JSON 长度 − 16384」，该条日志 N = 29,536,294，故原始长度 = 29,536,294 + 16,384。
  - 组成对它得上：该工作流当时的三个参考素材字节数为 19,878,018（参考视频 `8f326f68`）+ 1,292,809 + 989,256（两张参考图）= 22,160,083 字节，base64 膨胀 4/3 后为 29,546,777 字符，与实测 29,552,678 只差 5,901 字符（提示词和 JSON 结构），可认定膨胀源就是内联素材。
  - 链路：`web/src/services/api/video.ts` 的 `createVideoGenerationTask` 用 `imageToDataUrl` / `referenceMediaToFile` + `readFileAsDataUrl` 把素材转成 data URL，再交给 `web/src/services/api/generation.ts` 的 `requestServerGeneration` 一次性 `JSON.stringify` 提交；`server/src/ai/input.ts` 的 `imageInput` / `videoInput` 校验规则本身就要求 data URL（如 `/^data:video\/(mp4|webm);base64,…$/`），所以是**接口契约层面**的形状，不是某处实现写歪了。
  - 代价：浏览器每次生成都要重新读取并 base64 编码约 20MB 素材（`referenceMediaToFile` 会先 `getMediaBlob`、再 `readFileAsDataUrl`），建任务实测 17 秒；上游失败时同样白传一遍。
  - 服务端现状：只有参考图会被压缩（`server/src/ai/generation.ts` 的 `normalizeVideoImage`，超 512KB 转 JPEG），但那是**收到请求之后**才做，不减小请求体；参考视频完全没有压缩。`server/src/app.ts` 的 `express.json({ limit: Infinity })` 也没有请求体上限，超大请求会直接缓冲进内存。
  - 待定方向（未确认，不要直接改）：前端先 `POST /api/media` 上传素材，生成请求只传媒体 id，由服务端从媒体存储读出来转给上游；参考图的 512KB 压缩逻辑可以复用到这条路径。涉及接口契约、媒体归属校验和旧画布数据（节点里现有 `remote:` 引用仍需兼容读取），属于会改变实际行为的改动。
