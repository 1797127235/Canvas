# 线上部署

## 线上环境

- 生产站点：<http://openai2api.com:3015/>，健康检查 `/api/health` 返回 `{"ok":true}`。
- 部署机：`miaoda@192.168.6.78`（Windows，SSH 密钥登录，本机 `~/.ssh/config` 已有该主机）。
- 部署目录：`D:\infinite-canvas-v2`，**不是 git 仓库**。前后端代码由 GitHub Actions 构建进镜像，服务器只保留 compose、SQL 和 catalog 等运行期文件，并拉取镜像运行。
- Compose 栈（仓库根 `docker-compose.yml`）：`db`（PostgreSQL 16）、`api`（容器内 4100）、`web`（宿主 3015 → 容器 80）。
- 数据全部在 docker volume（`db_data`、`media_data`）和服务器本地的 `.env`、`backups/` 里，发布流程不触碰。

## 发布流程

1. 本地提交并推送 GitHub：

   ```bash
   git push origin main
   ```

2. GitHub Actions（`.github/workflows/publish-images.yml`）自动执行质量门禁（前端类型检查与测试、后端类型检查与测试），通过后构建两个镜像推送到 GHCR：

   - `ghcr.io/1797127235/infinite-canvas-web`
   - `ghcr.io/1797127235/infinite-canvas-api`

   标签：分支名、`sha-<短哈希>`（回滚用）、打 `v*` tag 时为版本号；`main` 上同时更新 `latest`。在仓库 Actions 页面确认 workflow 通过后再发布。

3. 服务器首次拉取私有镜像前需要登录 GHCR（用带 `read:packages` 权限的 PAT，只需做一次）：

   ```powershell
   docker login ghcr.io -u <GitHub 用户名> -p <PAT>
   ```

4. 服务器拉取新镜像并重启，不构建：

   ```powershell
   cd D:\infinite-canvas-v2
   docker compose pull
   docker compose up -d
   ```

5. 验证：`/api/health` 返回 `{"ok":true}`；`/templates/templates.json` 模板数量正确；随机抽一个模板封面或媒体文件返回 200。涉及生成链路的发布，再登录跑一单真实生成。

## 回滚

把服务器 `.env` 的 `IMAGE_TAG` 改成上一个 `sha-<短哈希>` 或版本号，再执行：

```powershell
docker compose pull
docker compose up -d
```

数据库结构变更目前只增不删，回滚旧版代码不影响数据。

## 需要同步到服务器的文件

前后端代码都在镜像里，常规发布不需要再传源码或打整包。只有下面这些运行期文件变化时才用 `scp -O` 同步：

- `docker-compose.yml`：compose 结构变化时。
- `server/sql/001-identity.sql`、`002-identity-rate-limits.sql`：`db-init` 从服务器目录读取，改动时需同步；`003~007` 由 api 镜像内部读取，不需要同步。
- `server/config/catalog.json`：上游目录格式变化时（见下方注意事项）。

## 接口审计日志

api 对每个 `/api` 请求输出一行 JSON 日志（pino，stdout），包含方法、路径、状态码、耗时、账号 id、脱敏后的请求体和截断后的响应体；登录密码输出为 `[redacted]`，账号 API Key 只留前 6 位，请求体超过 16KiB、响应体超过 4KiB 截断，媒体接口只记元信息，`/api/health` 不记。查看与排查：

```powershell
docker logs --tail 100 infinite-canvas-v2-api-1
# 按路径过滤
docker logs --since 1h infinite-canvas-v2-api-1 | Select-String "POST /api/generations"
```

api 容器日志轮转单独放大为 50MB × 10 个文件（约 500MB），其余容器仍为 10MB × 3；`LOG_LEVEL` 环境变量可调日志级别（默认 `info`）。注意日志含用户提示词等业务内容，属敏感数据，不要外发原始日志。

## 注意事项

- **`APP_ORIGIN` 必须和浏览器实际访问的来源一致**（协议 + 域名 + 端口，只支持一个值）。换域名或端口访问时，同步改服务器 `.env` 里的 `APP_ORIGIN` 并 `docker compose up -d` 重建 api，否则所有写操作（登录、保存、生成）都会被同源校验以 403「请求来源不受信任」拒绝；读操作和页面不受影响。
- **catalog.json 是 api 容器的挂载文件**：不随镜像更新，以服务器上的版本为准。但如果代码改了目录格式要求（例如 AI SDK 适配层要求 `gateway-videos` / `xai-videos` 等 adapter 字段），必须把仓库的 `server/config/catalog.json` 单独 `scp -O` 过去再重启 api，否则 api 启动报 `Invalid catalog configuration` 并崩溃循环。api 起不来先查容器日志里的这个报错。
- `.env`（`WEB_PORT=3015`、`POSTGRES_PASSWORD`、`CREDENTIALS_ENCRYPTION_KEY`、`RATE_LIMIT_SECRET`、`IMAGE_API`、`IMAGE_WEB`、`IMAGE_TAG` 等）只存在于服务器，不在 git 里，也不在镜像里；不要把它的内容写进仓库。
- `IMAGE_TAG` 决定服务器跑哪个镜像，建议固定成 workflow 产出的 `sha-<短哈希>` 或版本号，不要长期停在 `latest`；`latest` 只代表 main 的最新构建，无法判断线上实际版本。
- **首次从本地构建切换到镜像拉取时**，服务器 `.env` 里原来指向本地镜像的 `IMAGE_TAG`（如 `dc131b4`）或 `local` 在 GHCR 里并不存在，必须先改成镜像仓库里真实存在的标签（`latest` 或某个 `sha-<短哈希>`），否则 `docker compose pull` 会报 manifest unknown。切换后旧的本地镜像可以 `docker image prune` 清理。
- 数据库表由 db-init 和后端启动迁移维护；`db` 容器保持运行，不要随发布重建，账号、画布和媒体数据都在它的 volume 里。
- 服务器 PowerShell 控制台是 GBK 编码，直接 `Get-Content` 查看 UTF-8 中文文件会乱码，看起来像文件坏了；校验内容用 ASCII 字符串（例如模板 id）或比对 SHA256。
- 发布完成后浏览器强刷一次，确认模板库和画布正常。
