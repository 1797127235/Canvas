# 线上部署

## 线上环境

- 生产站点：<http://openai2api.com:3015/>，健康检查 `/api/health` 返回 `{"ok":true}`。
- 部署机：Windows `miaoda@192.168.6.78:22`；公网 SSH `miaoda@openai2api.com:2222` 登录该机 WSL，自动部署使用后者。
- 部署目录：Windows `D:\infinite-canvas-v2`，WSL 对应 `/mnt/d/infinite-canvas-v2`，**不是 git 仓库**，只保留 compose、SQL、catalog 等运行期文件。
- 构建目录：`/mnt/d/infinite-canvas-build`，发布时把源码同步到这里，并在部署机上本地构建镜像。
- Compose 栈（仓库根 `docker-compose.yml`）：`db`（PostgreSQL 16）、`api`（容器内 4100）、`web`（宿主 3015 → 容器 80）。
- 数据位于 Docker volume（`db_data`、`media_data`），配置位于服务器 `.env` 和 catalog；部署只新增备份，不删除业务数据或覆盖私有配置。

## 快速部署（推荐）

在仓库里一条命令完成：同步源码 → 部署机本地构建镜像 → 只切换 `api` / `web` → 校验健康接口。

```bash
bash scripts/deploy-local.sh
```

- 全程约 2~4 分钟：rsync 源码（首次约 60MB，之后只传改动）+ 部署机 20 核并行构建两个镜像 + 重建两个容器。
- 镜像只在部署机本地构建，不推也不拉任何镜像仓库，所以完全不受境外镜像下载速度影响。
- 镜像标签是 `infinite-canvas-api:local-<短提交>` / `infinite-canvas-web:local-<短提交>`，并带 `org.opencontainers.image.revision` 提交标签；部署脚本核对标签，不一致直接拒绝切换。
- 可覆盖的环境变量：`DEPLOY_TARGET`（默认 `miaoda@openai2api.com`）、`DEPLOY_PORT`（默认 `2222`，置空表示不加 `-p`，配合 SSH 别名使用）、`DEPLOY_PROJECT`（默认 `/mnt/d/infinite-canvas-v2`）、`DEPLOY_BUILD_DIR`（默认 `/mnt/d/infinite-canvas-build`）、`DEPLOY_PUBLIC_URL`（默认 `http://openai2api.com:3015`）。
- 默认不做数据库快照以换速度；需要时加 `DEPLOY_DB_BACKUP=1`，切换前会把 `pg_dump` 写进本次备份目录。
- 工作区有未提交改动时只打印警告，镜像仍按 `HEAD` 提交标记。

部署机侧脚本 `scripts/deploy.sh` 依次做：文件锁互斥 → 校验两个镜像已构建且提交标签一致 → 把旧 compose 和旧镜像 ID 记到 `backups/deploy-<时间>-<短 SHA>/` → 同步 `docker-compose.yml` 与 001/002 初始化 SQL → 写 `docker-compose.deploy.yml` 覆盖文件 → 只重建 `api`/`web`（`--no-deps --pull never --force-recreate --wait`）→ 检查健康接口、首页和模板索引。服务器 `.env`、catalog、媒体和数据库卷保持不变。

## CI 自动部署（可选）

`.github/workflows/publish-images.yml` 推送到 `main` 后先跑质量门禁（两端类型检查、前端测试、后端 PostgreSQL 集成测试、部署脚本回归测试），通过后并行两个 job：

1. `deploy` 走和本地完全相同的一条路径：rsync 源码到部署机 → 本地构建 → 切换容器，不再 `docker save | ssh docker load` 传镜像。PR 不部署；版本 tag 只发布镜像；手动运行工作流并勾选 `deploy_production` 也走这条路径。
2. `publish` 把两个镜像推到 GHCR 作为归档和回滚参考，标签为分支名、`sha-<短哈希>`、`sha-<完整 40 位 SHA>`、`latest`（仅默认分支）。归档失败不影响已完成的部署。

仓库未配置下面两个 Secrets 时 `deploy` job 会立即失败，直接用上面的本地命令部署即可。

## CI 凭据配置（仅 CI 需要）

GitHub 仓库设置 → Environments → `production`，仅允许 `main` 分支部署。添加环境 Secrets：

- `DEPLOY_SSH_KEY`：专用 Ed25519 部署私钥，不复用个人 SSH Key。
- `DEPLOY_KNOWN_HOSTS`：`[openai2api.com]:2222` 的固定 Ed25519 主机公钥，必须经可信通道核对指纹。

对应公钥加入生产 WSL 的 `~/.ssh/authorized_keys`，使用 `restrict` 禁止端口转发、代理转发和 PTY。部署用户需要 Docker 权限；私钥仍具备该用户的命令执行能力，应仅授予生产工作流。CI 不采用动态 `ssh-keyscan` 或关闭主机验证。

## 失败恢复与手工回滚

启动或健康检查失败时，脚本自动把覆盖文件切回部署前容器实际镜像 ID（`{{.Image}}`）并重新拉起，不自动恢复数据库。数据库迁移需与旧版本兼容；破坏性迁移必须另行备份、演练和人工决策，不能依赖镜像回滚保证数据安全。

生产版本以 `docker-compose.deploy.yml` 覆盖文件和容器 revision label 为准，不依赖 `.env` 中的 `IMAGE_TAG`。手工维护必须同时指定两个 Compose 文件：

```bash
cd /mnt/d/infinite-canvas-v2
docker compose -p infinite-canvas-v2 -f docker-compose.yml -f docker-compose.deploy.yml ps
```

手工回滚：选定一次部署备份，恢复其中的 `docker-compose.yml`，把 `previous-images.txt` 的两行完整镜像引用分别写入覆盖文件的 `api.image` / `web.image`（本地镜像 ID 或 `local-<短 SHA>` 标签），然后执行：

```bash
docker compose -p infinite-canvas-v2 -f docker-compose.yml -f docker-compose.deploy.yml up -d --no-deps --pull never --force-recreate --wait --wait-timeout 120 api web
curl --fail http://127.0.0.1:3015/api/health
```

不要执行 `docker compose down -v`，不要通过发布脚本清理镜像或历史备份。自动部署使用 GitHub 并发组和 WSL 文件锁避免两个部署并行；手工维护前也要确认没有部署正在运行。

## 运行文件同步边界

- 同步：`docker-compose.yml`、`server/sql/001-identity.sql`、`002-identity-rate-limits.sql`；构建目录还会带上 `web/`、`server/` 等构建所需源码。
- rsync 排除：`.git`、`node_modules`、`dist`、`.env` 与 `.env.*`、`backups`、`*.log`、`.vscode`、`.claude`。
- API 镜像内的后续 SQL 在 API 启动时处理，不从发布包同步整份 `server/`。
- 不同步：服务器 `.env`、`backups/`、媒体和 `server/config/catalog.json`。
- catalog 格式变更必须单独核对服务器配置并显式同步，否则可能导致 `Invalid catalog configuration`；普通发布禁止覆盖账号上游配置。

## 接口审计日志

api 对每个 `/api` 请求输出一行 JSON 日志（pino，stdout），包含方法、路径、状态码、耗时、账号 id、脱敏后的请求体和截断后的响应体；登录密码输出为 `[redacted]`，账号 API Key 只留前 6 位，请求里的参考素材（`data:` URL）和生图结果里的 base64 图片只记 MIME 与字节数、不落原始字节，请求体超过 16KiB、响应体超过 4KiB 截断，媒体接口只记元信息，`/api/health` 不记。查看与排查：

```powershell
docker logs --tail 100 infinite-canvas-v2-api-1
# 按路径过滤
docker logs --since 1h infinite-canvas-v2-api-1 | Select-String "POST /api/generations"
```

api 容器日志轮转单独放大为 50MB × 10 个文件（约 500MB），其余容器仍为 10MB × 3；`LOG_LEVEL` 环境变量可调日志级别（默认 `info`）。注意日志含用户提示词等业务内容，属敏感数据，不要外发原始日志。

## 注意事项

- **`APP_ORIGIN` 必须和浏览器实际访问的来源一致**（协议 + 域名 + 端口，只支持一个值）。换域名或端口访问时，同步改服务器 `.env` 里的 `APP_ORIGIN` 并使用两个 Compose 文件执行 `up -d --no-deps api` 重建 api，否则所有写操作（登录、保存、生成）都会被同源校验以 403「请求来源不受信任」拒绝；读操作和页面不受影响。
- **catalog.json 是 api 容器的挂载文件**：不随镜像更新，以服务器上的版本为准。但如果代码改了目录格式要求（例如 AI SDK 适配层要求 `providerId` 等字段），必须把仓库的 `server/config/catalog.json` 单独 `scp -O` 过去再重启 api，否则 api 启动报 `Invalid catalog configuration` 并崩溃循环。api 起不来先查容器日志里的这个报错。
- `.env`（`WEB_PORT=3015`、`POSTGRES_PASSWORD`、`CREDENTIALS_ENCRYPTION_KEY`、`RATE_LIMIT_SECRET` 等）只存在于服务器，不在 git 里，也不在镜像里；不要把它的内容写进仓库。
- 部署一律写 `docker-compose.deploy.yml` 覆盖文件，固定成本次构建的镜像；`.env` 里的 `IMAGE_API` / `IMAGE_WEB` / `IMAGE_TAG` 只在没有覆盖文件时生效，不再是线上版本凭据。
- 部署全程只用本地镜像（`--pull never`），不访问任何镜像仓库，因此不会触发 Windows `wincred` 凭据助手失败。只有手工执行 `docker compose pull` 才可能遇到 `A specified logon session does not exist`：那是机器级 `DOCKER_CONFIG` 指向带 `credsStore=wincred` 的配置导致，改为 `docker pull` 单独拉取再 `docker compose up -d --pull never` 即可。
- 数据库表由 db-init 和后端启动迁移维护；`db` 容器保持运行，不要随发布重建，账号、画布和媒体数据都在它的 volume 里。
- 服务器 PowerShell 控制台是 GBK 编码，直接 `Get-Content` 查看 UTF-8 中文文件会乱码，看起来像文件坏了；校验内容用 ASCII 字符串（例如模板 id）或比对 SHA256。
- 发布完成后浏览器强刷一次，确认模板库和画布正常。
