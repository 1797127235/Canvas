# 线上部署

## 线上环境

- 生产站点：<http://openai2api.com:3015/>，健康检查 `/api/health` 返回 `{"ok":true}`。
- 部署机：Windows `miaoda@192.168.6.78:22`；公网 SSH `miaoda@openai2api.com:2222` 登录该机 WSL，自动部署使用后者。
- 部署目录：Windows `D:\infinite-canvas-v2`，WSL 对应 `/mnt/d/infinite-canvas-v2`，**不是 git 仓库**。前后端代码由 GitHub Actions 构建进镜像，服务器只保留 compose、SQL 和 catalog 等运行期文件，并拉取镜像运行。
- Compose 栈（仓库根 `docker-compose.yml`）：`db`（PostgreSQL 16）、`api`（容器内 4100）、`web`（宿主 3015 → 容器 80）。
- 数据位于 Docker volume（`db_data`、`media_data`），配置位于服务器 `.env` 和 catalog；部署只新增备份，不删除业务数据或覆盖私有配置。

## 自动发布流程

1. 推送到 `main` 后，`.github/workflows/publish-images.yml` 先执行两端类型检查、测试、PostgreSQL 集成测试和部署脚本回归测试，再构建 Web/API 镜像并发布到 GHCR。
2. 两个镜像都成功后，`deploy` job 使用 `production` 环境密钥，经 `miaoda@openai2api.com:2222` 登录 WSL，运行 `scripts/deploy.sh`。PR 只验证；版本 tag 只发布镜像，不自动部署。手动运行工作流并选择 `main` 也会部署。
3. GitHub runner 拉取本次 `sha-<完整 40 位 SHA>` 镜像，经 `docker save | gzip | SSH docker load` 导入生产机；生产机不直接访问 GHCR。Runner 单镜像拉取超时 180 秒，传输超时 420 秒；生产脚本校验镜像提交标签。短 SHA、分支名和 `latest` 标签仍发布，但生产不依赖可变标签。
4. 在 `backups/deploy-<时间>-<短 SHA>/` 新建 PostgreSQL 快照、旧 Compose 配置和旧镜像记录，不清理已有备份。数据库备份失败则停止部署。
5. 同步仓库的 `docker-compose.yml` 和初始化 SQL 001/002；镜像写入独立的 `docker-compose.deploy.yml` 覆盖文件。服务器 `.env`、catalog、媒体和数据库卷保持不变。
6. 仅重建 `api` / `web`，使用 `--no-deps --pull never --force-recreate --wait`，不重启数据库或 db-init。检查健康接口、首页和模板索引，最后从 GitHub runner 检查公网健康接口。
7. 远端启动或本机健康检查失败时，恢复旧 Compose 和应用镜像，并让 Actions 报失败；公网探测失败会标红，需检查网络或服务，不会自动恢复数据库。

```bash
git push origin main
```

当前脚本用于已有生产栈升级，不负责首次安装、密钥生成或数据库首次初始化。两包目前公开，由 GitHub runner 拉取后传入生产机，绕过生产 Docker 的 GHCR 代理下载阻塞；生产仍使用临时空凭据配置，不调用 wincred。改为私有包时需给 runner 配置只读 GHCR 凭据。

## 首次凭据配置

GitHub 仓库设置 → Environments → `production`，仅允许 `main` 分支部署。添加环境 Secrets：

- `DEPLOY_SSH_KEY`：专用 Ed25519 部署私钥，不复用个人 SSH Key。
- `DEPLOY_KNOWN_HOSTS`：`[openai2api.com]:2222` 的固定 Ed25519 主机公钥，必须经可信通道核对指纹。

对应公钥加入生产 WSL 的 `~/.ssh/authorized_keys`，使用 `restrict` 禁止端口转发、代理转发和 PTY。部署用户需要 Docker 权限；私钥仍具备该用户的命令执行能力，应仅授予生产工作流。CI 不采用动态 `ssh-keyscan` 或关闭主机验证。

## 失败恢复与手工回滚

自动恢复使用部署前容器实际镜像 ID（`{{.Image}}`），即使原标签被重建覆盖也不会切错版本；不自动恢复数据库。数据库迁移需与旧版本兼容；破坏性迁移必须另行备份、演练和人工决策，不能依赖镜像回滚保证数据安全。

生产版本以覆盖文件和容器 revision label 为准，不再依赖 `.env` 中的 `IMAGE_TAG`。手工维护必须同时指定两个 Compose 文件，避免切回 `.env` 的旧标签：

```bash
cd /mnt/d/infinite-canvas-v2
docker compose -p infinite-canvas-v2 -f docker-compose.yml -f docker-compose.deploy.yml ps
```

手工回滚：选定一次部署备份，恢复其中的 `docker-compose.yml`，将 `previous-images.txt` 的两行完整镜像引用分别写入覆盖文件的 `api.image` / `web.image`。需要下载旧镜像时分别 `docker pull <镜像引用>`；然后运行：

```bash
docker compose -p infinite-canvas-v2 -f docker-compose.yml -f docker-compose.deploy.yml up -d --no-deps --pull never --force-recreate --wait --wait-timeout 120 api web
curl --fail http://127.0.0.1:3015/api/health
```

不要执行 `docker compose down -v`，不要通过发布脚本清理镜像或历史备份。自动部署使用 GitHub 并发组和 WSL 文件锁避免两个自动部署并行；手工维护前也要确认没有部署正在运行。

## 运行文件同步边界

- 自动同步：`docker-compose.yml`、`server/sql/001-identity.sql`、`002-identity-rate-limits.sql`。
- API 镜像内的后续 SQL 在 API 启动时处理，不从发布包同步整份 `server/`。
- 不同步：服务器 `.env`、`backups/`、媒体和 `server/config/catalog.json`。
- catalog 格式变更必须单独核对服务器配置并显式同步，否则可能导致 `Invalid catalog configuration`；普通发布禁止覆盖账号上游配置。

## 接口审计日志

api 对每个 `/api` 请求输出一行 JSON 日志（pino，stdout），包含方法、路径、状态码、耗时、账号 id、脱敏后的请求体和截断后的响应体；登录密码输出为 `[redacted]`，账号 API Key 只留前 6 位，请求里的参考素材（`data:` URL）和生图结果里的 base64 图片只记 MIME 与字节数、不落原始字节，请求体超过 16KiB、响应体超过 4KiB 截断，媒体接口只记元信息，`/api/health` 不记。查看与排查：

```powershell
docker logs --tail 100 infinite-canvas-v2-api-1
# 按路径过滤
docker logs --since 1h infinite-canvas-v2-api-1 | Select-String "POST /api/generations"
```

api 容器日志轮转单独放大为 50MB × 10 个文件（约 500MB），其余容器仍为 10MB × 3；`LOG_LEVEL` 环境变量可调日志级别（默认 `info`）。注意日志含用户提示词等业务内容，属敏感数据，不要外发原始日志。

## 注意事项

- **`APP_ORIGIN` 必须和浏览器实际访问的来源一致**（协议 + 域名 + 端口，只支持一个值）。换域名或端口访问时，同步改服务器 `.env` 里的 `APP_ORIGIN` 并使用两个 Compose 文件执行 `up -d --no-deps api` 重建 api，否则所有写操作（登录、保存、生成）都会被同源校验以 403「请求来源不受信任」拒绝；读操作和页面不受影响。
- **catalog.json 是 api 容器的挂载文件**：不随镜像更新，以服务器上的版本为准。但如果代码改了目录格式要求（例如 AI SDK 适配层要求 `gateway-videos` / `xai-videos` 等 adapter 字段），必须把仓库的 `server/config/catalog.json` 单独 `scp -O` 过去再重启 api，否则 api 启动报 `Invalid catalog configuration` 并崩溃循环。api 起不来先查容器日志里的这个报错。
- `.env`（`WEB_PORT=3015`、`POSTGRES_PASSWORD`、`CREDENTIALS_ENCRYPTION_KEY`、`RATE_LIMIT_SECRET`、`IMAGE_API`、`IMAGE_WEB`、`IMAGE_TAG` 等）只存在于服务器，不在 git 里，也不在镜像里；不要把它的内容写进仓库。
- 自动部署后 `docker-compose.deploy.yml` 的固定 SHA 镜像优先于 `.env` 的 `IMAGE_TAG`；手工运行 Compose 必须带此覆盖文件。`latest` 仅表示 main 最新构建，不是线上版本凭据。
- **首次从本地构建切换到镜像拉取时**，服务器 `.env` 里原来指向本地镜像的 `IMAGE_TAG`（如 `dc131b4`）或 `local` 在 GHCR 里并不存在，必须先改成镜像仓库里真实存在的标签（`latest` 或某个 `sha-<短哈希>`），否则 `docker compose pull` 会报 manifest unknown。自动部署通过固定 SHA 覆盖文件选择镜像，不修改 `.env`；保留旧应用镜像供回滚，不自动 prune。
- **Windows SSH 会话使用原凭据配置时，`docker compose pull` 会失败**，报 `error getting credentials - err: exit status 1, out: 'A specified logon session does not exist. It may already have been terminated.'`。原因是服务器机器级环境变量 `DOCKER_CONFIG` 指向 `D:\data-crawling-group\docker-client-config`，其 `config.json` 配了 `credsStore=wincred`，而 wincred 只在交互式登录会话（RDP 桌面）可用；compose 又会把 `docker-compose.yml` 里所有镜像（含 `docker.io` 的 `postgres:16-alpine`）都过一遍凭据助手，因此整条命令直接失败，和包是否公开无关。绕过办法是用 `docker pull` 单独拉 ghcr 的两个镜像（公开包匿名可拉），再 `docker compose up -d --pull never`，此时 compose 不访问仓库、不触发凭据助手；`postgres:16-alpine` 服务器本地已有，不需要重新拉。
- 数据库表由 db-init 和后端启动迁移维护；`db` 容器保持运行，不要随发布重建，账号、画布和媒体数据都在它的 volume 里。
- 服务器 PowerShell 控制台是 GBK 编码，直接 `Get-Content` 查看 UTF-8 中文文件会乱码，看起来像文件坏了；校验内容用 ASCII 字符串（例如模板 id）或比对 SHA256。
- 发布完成后浏览器强刷一次，确认模板库和画布正常。
